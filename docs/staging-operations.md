# คู่มือดูแล staging

อัปเดต 11 พฤศจิกายน 2026 สำหรับ Mini-ERP ที่ใช้ข้อมูลสมมติ ยังไม่เชื่อม Express/DBF ผู้ดูแลคือเจ้าของโปรเจกต์ งานตามตารางด้านล่างทำเอง ยังไม่ได้ตั้ง schedule หรือระบบสำรองอัตโนมัติ

## จุดที่ใช้ตรวจ

- เว็บ: https://mini-erp2-staging.onrender.com (ต้องมีรหัสผ่าน)
- Health: https://mini-erp2-staging.onrender.com/api/health (สาธารณะ)
- Render: https://dashboard.render.com — web `mini-erp2-staging`, database `mini-erp2-staging-db`
- UptimeRobot: https://dashboard.uptimerobot.com — monitor ของ URL health ด้านบน
- CI: https://github.com/Brownstone42/mini-erp2/actions/workflows/ci.yml

เก็บรหัสผ่านและ Database URL ในที่เก็บรหัสผ่านส่วนตัว ไม่บันทึกในคู่มือ Git ภาพหน้าจอ หรือข้อความแจ้งปัญหา

## สิ่งที่ยืนยันแล้ว

| รายการ | หลักฐานและขอบเขต |
| --- | --- |
| UptimeRobot | ภาพของผู้ใช้แสดง URL `/api/health`, Up และ Checked every 5m |
| อีเมล UptimeRobot | ผู้ใช้ยืนยันได้รับ Test Notification แล้ว ยังไม่ได้จำลอง outage จริง |
| Render notifications | ผู้ใช้ตั้ง Service Notifications เป็น Only failure notifications; ยังไม่ได้ยืนยันการส่งอีเมลจากเหตุขัดข้องจริง |
| Render Recovery | ภาพหน้าจอแสดง Point-in-Time Recovery ย้อนหลัง 3 วัน และ Export เก็บอย่างน้อย 7 วัน; ยังไม่ได้กดกู้คืนผ่าน Render |
| Application rollback | ซ้อม B → protected A ผ่าน วันทบทวน 26 พ.ย. 2026 ยังอยู่ และการป้องกันยังทำงาน ดู [หลักฐาน rollback](staging-access.md) |
| Backup/restore | สำรอง staging และกู้ลงฐาน Docker แยกผ่าน ข้อมูลและ migration history ตรงกัน ดู [หลักฐานและคำสั่ง](backup-restore.md) |
| หน้าจอหลัง deploy รอบถัดมา | ผู้ใช้รายงานว่าไม่มีข้อความรุ่น B และวันทบทวนยังเป็น 26 พ.ย. 2026; ไม่ได้ตรวจ live commit SHA โดยตรง |

Health เช็กการเข้าถึงแอปและฐานข้อมูล ไม่ยืนยันการล็อกอิน การบันทึกวัน หรือความถูกต้อง/ความสดของข้อมูลธุรกิจทั้งหมด

## เมื่อได้รับแจ้งเตือน

1. ดู URL และเวลาในอีเมล เปิด monitor เพื่อดูว่าเหตุยังเกิดอยู่หรือกลับเป็น Up แล้ว
2. เปิด health URL ควรได้ HTTP 200 และ `{"status":"ok"}` จากนั้นเปิดเว็บเพื่อเช็กการใช้งานจริง หาก health ผ่านแต่หน้าเว็บมีปัญหา ให้ตรวจต่อ
3. เปิด Render ของ web ดู Events/ประวัติ deploy และ Logs ช่วงเวลาเดียวกัน แล้วตรวจสถานะฐานข้อมูล บันทึกข้อความผิดพลาดโดยตัดข้อมูลลับออก
4. ถ้าเกิดหลัง deploy และเป็นปัญหาโค้ด ให้พิจารณา rollback ตามขั้นตอนด้านล่าง ถ้าเป็นปัญหาฐานข้อมูลหรือข้อมูลผิด อย่า restore ทับฐานเดิมเพื่อทดลอง
5. หลังแก้ ตรวจ health, หน้าล็อกอิน, หน้ารายงาน และการบันทึกวันใน staging แล้วเปิดใหม่ บันทึกเวลาและผลจริง ตรวจว่า monitor กลับเป็น Up

## Deploy และ rollback

ก่อน deploy ให้ CI ของ commit เป้าหมายผ่าน จด commit/deployment เดิมและวันทบทวนปัจจุบัน คง Auto-Deploy เป็น Off ถ้ามี migration ให้สำรองข้อมูลก่อนและตรวจว่าโค้ดเดิมยังใช้ schema ใหม่ได้หรือไม่

หากต้อง rollback ให้เปิดประวัติ deploy ใน Render เลือกรุ่นที่เคยผ่านและมีการป้องกัน staging ตรวจ Environment ของรุ่นเป้าหมายก่อนดำเนินการ ดู [คู่มือ rollback แบบเต็ม](staging-access.md)

- ห้ามย้อนเป็นรุ่นที่ไม่มีการป้องกัน `a25ec1e` หรือ `30dd528`
- หลัง rollback เปิด private session ใหม่ ต้องถามรหัสผ่าน และ health ต้องผ่าน
- วันทบทวนต้องตรงกับค่าที่จดไว้ก่อน rollback ไม่จำเป็นต้องเป็น 26 พ.ย. เสมอไปเมื่อมีการเปลี่ยนข้อมูลภายหลัง
- Rollback แอปไม่ใช่การย้อนข้อมูล หลักฐานที่มีครอบคลุมเฉพาะกรณี schema ไม่เปลี่ยน หากมี migration ต้องประเมินแผนกู้คืนแยกก่อน

## ตารางดูแลแบบทำเอง

| เมื่อไร | งาน | เกณฑ์สำเร็จ |
| --- | --- | --- |
| ทุกครั้งที่มี alert | ตรวจตามขั้นตอนด้านบน | ระบุสาเหตุ/วิธีแก้และตรวจระบบหลังแก้ |
| สัปดาห์ละครั้ง | รันคำสั่งใน [คู่มือ backup/restore](backup-restore.md) ขณะ Docker เปิด | report เป็น PASS, ข้อมูลต้นทาง/ปลายทางตรง และต้นทางไม่เปลี่ยน |
| ก่อนเปลี่ยน schema | สำรองเพิ่มและทบทวน migration/rollback | มี archive และ report ที่ผ่านก่อนเปลี่ยน |
| เดือนละครั้ง | ทบทวนผลซ้อมกู้คืนล่าสุดและลองอ่านรายงานผล ตรวจพื้นที่ backup/volume | มีหลักฐานกู้คืนที่ผ่านในเดือนนั้นและทราบที่เก็บ |
| หลัง deploy | ตรวจ auth, health, รายงานและวันทบทวน | บันทึก commit และผลตรวจ |

สคริปต์ปัจจุบันทำทั้ง backup และ restore ลง Docker แยกในครั้งเดียว ดังนั้นการสำรองประจำสัปดาห์ที่ผ่านก็เป็นการซ้อมกู้คืนด้วย หากข้ามรอบประจำสัปดาห์ ต้องรันอย่างน้อยในรอบตรวจรายเดือน ไม่ใช้ `--self-test` แทนหลักฐานสำรอง staging จริง

เก็บชุดสำรองประจำสัปดาห์ที่ผ่านล่าสุดอย่างน้อย 4 ชุด พร้อม `report.json` และเก็บชุดก่อนเปลี่ยน schema จนตรวจรับการเปลี่ยนแปลงเรียบร้อยก่อนพิจารณาลบ ตรวจชื่อ container/volume จาก report ของชุดนั้นก่อนทำความสะอาด ไม่ใช้คำสั่ง prune รวม ไม่มีการลบไฟล์หรือ volume อัตโนมัติ

ไฟล์อยู่ใน `.backups/` บนเครื่องนี้ สคริปต์ไม่ได้เข้ารหัสและยังไม่มีสำเนานอกเครื่อง หากเครื่องเสียอาจเสียไฟล์สำรองด้วย รอบสัปดาห์อาจมีช่องว่างข้อมูลถึงหนึ่งสัปดาห์เมื่อจำเป็นต้องพึ่งไฟล์เหล่านี้ ก่อนใช้ข้อมูลจริงต้องตกลงระยะข้อมูลที่ยอมสูญเสียได้ และจัดเก็บสำรองนอกเครื่องแยกจากเวลา downtime ที่ยอมรับได้

## หากต้องกู้ข้อมูลจริง

หยุดการแก้ข้อมูลระหว่างตรวจเหตุ จดเวลาที่ข้อมูลยังถูกต้องและ timezone เก็บหลักฐานต้นทางไว้ แล้วเลือกวิธีกู้ตามเหตุ

- Render PITR: หน้า Recovery ที่ตรวจแสดงช่วงย้อนหลัง 3 วัน การกู้จะสร้างฐานใหม่ให้ตรวจแยกก่อนเปลี่ยน connection ของแอป ต้องตรวจแพ็กเกจและค่าใช้จ่ายก่อนกดสร้าง
- ไฟล์สำรอง: กู้ลงฐานว่างแยกก่อน เปรียบเทียบข้อมูลและ migration history แล้วจึงวางแผนย้ายแอป ไม่รัน restore ทับ staging เดิม

การซ้อมที่ผ่านแล้วตรวจข้อมูลด้วย SQL ยังไม่ได้เปิดแอปชี้ฐานที่กู้คืน ไม่ได้ยืนยัน recovery เต็มระบบหรือเปลี่ยน connection จริงในรอบนี้

อ้างอิง: [Render Postgres Recovery and Backups](https://render.com/docs/postgresql-backups) ตรวจเมื่อ 11 พฤศจิกายน 2026; ช่วงเวลา Recovery ของบัญชีนี้ยืนยันจากภาพผู้ใช้ประกอบด้วย
