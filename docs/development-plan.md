# Mini-ERP V2 แผนพัฒนาด้วย Next.js

อัปเดตหลัง R2: ผู้ใช้ตรวจรับหน้าจอแล้ว ติดตั้ง WSL/Docker สำเร็จ และทำขั้น 6 ด้วยชุด Docker แยกฐานเดิมแล้ว ตรวจ build, migration, health และบันทึกวันหลัง down/up ผ่าน ดู [คู่มือและผลตรวจ Docker](docker-local.md) ขั้น 7 เตรียม workflow ตรวจ TypeScript, logic tests, production build และ browser tests กับ PostgreSQL ชั่วคราวแล้ว ดู [คู่มือ CI](ci.md) ยังต้องระบุ GitHub repository เพื่อเปิดใช้งานจริง ส่วน lint ยังไม่ได้เพิ่ม ยังไม่ deploy หรือเชื่อม DBF

สถานะล่าสุด: ผู้ใช้ยืนยัน R2 และให้ทำ AT ทุกเคสแล้ว หน้าหลักยอดสั่งรายเดือน ค้างส่งรวมไม่จำกัดเวลา และหน้ารายละเอียดทำงานด้วยข้อมูลสมมติ มีหลักฐาน AT-R2-01 ถึง AT-R2-20 ใน [ผลตรวจ R2](r2-validation.md) PostgreSQL ยังรันแบบ local เป็นทางสำรอง ไม่ได้ตรวจ Docker

ตารางขั้นตอนด้านล่างเป็นแผนตั้งต้นก่อน R2 ขั้น 1–4 ทำแล้วโดยมีการปรับ requirement เป็นยอดสั่งและกิจการคลังเดียว ขั้นถัดไปคือให้ผู้ใช้ตรวจหน้าตามขั้น 5 ก่อนเดินต่อ Docker/CI/deploy ไม่เชื่อม DBF ในรอบนี้

เป้าหมายแรกคือหน้าทบทวนการเติมสต็อกของ Manager สำหรับถุงมือ Vinyl หนึ่ง SKU หนึ่งคลัง โดยเริ่มจาก acceptance test และข้อมูลสมมติ เมื่อหน้าพร้อมให้ผู้ใช้ตรวจแล้วจึงเดินต่อเรื่อง Docker, CI/CD, staging และ rollback

## วิธีพัฒนาในแต่ละรอบ

1. เขียน test ตามพฤติกรรมที่ต้องการและอ้างอิงรหัส AT เดิม
2. รันและเห็น test ล้มเหลวเพราะพฤติกรรมยังไม่มี ไม่ใช่เพราะตั้งค่าเครื่องมือผิด
3. เขียนโค้ดให้ test ผ่าน
4. ปรับโครงสร้างโค้ดโดย test ยังผ่าน

ใช้ชุดข้อมูลสมมติเดิม ตรึงเวลาทดสอบไว้ที่ 10 พฤศจิกายน 2026 เวลา 09:00 น. ประเทศไทย (Asia/Bangkok) และแยกข้อมูลของแต่ละกรณีเพื่อไม่ให้ผลขึ้นกับลำดับการรัน

## ขั้นตอนและเกณฑ์จบ

| ขั้น | งาน | เกณฑ์จบ |
| --- | --- | --- |
| 1 | ตั้งโครงทดสอบ TypeScript และ Vitest ขั้นต่ำ สร้างข้อมูลสมมติ แล้วเขียน AT-01 ก่อน logic จริง | เห็น test ล้มเหลวตามเหตุผลที่คาดสำหรับกรณีสั่ง 100 ส่งจริง 60 ค้างส่ง 40 |
| 2 | เขียน logic ให้ AT-01 ผ่าน แล้วเพิ่มการรวมยอดรายเดือน แยกบริษัท กรอง SKU/คลัง และสถานะข้อมูลทีละกรณี | กรณีข้อมูลผ่าน รวมยอดส่งจริง 110 กล่อง ค้างส่ง 70 กล่อง และคงเหลือ 150 กล่องตามชุดหลัก |
| 3 | เพิ่ม PostgreSQL และ Prisma ใช้ Compose รันฐานข้อมูลสำหรับพัฒนา เขียน test ก่อนทำการตั้งและเปลี่ยนวันทบทวน | AT-12 และ AT-13 ผ่านในระดับฐานข้อมูล อ่านวันที่กลับจากการเรียกครั้งใหม่ได้ |
| 4 | สร้างหน้าจอ Next.js แสดงตาราง 12 เดือน ยอดคงเหลือ ค้างส่ง MOQ/lead time และฟอร์มวันทบทวน เพิ่ม Playwright test ก่อนทำพฤติกรรมหน้าจอ | AT ทั้ง 14 ข้อมีหลักฐานผ่านในระดับที่เหมาะสม และ browser test ตรวจตัวอย่างส่งจริง 60 ค้างส่ง 40 รวมถึงบันทึกวันแล้วเปิดหน้าใหม่ได้ |
| 5 | ให้ผู้ใช้ตรวจหน้าที่ใช้ข้อมูลสมมติ | ผู้ใช้ตรวจยอด ข้อความสถานะ และการตั้งวันทบทวน พร้อมให้ข้อสรุปก่อนเดินต่อ |
| 6 | บรรจุแอปด้วย Docker และ Compose เพิ่ม environment configuration, health check และคู่มือรัน | รันจากสภาพแวดล้อมใหม่ได้ และ restart แล้ววันทบทวนยังอยู่ |
| 7 | ทำ CI ด้วย GitHub Actions ให้ตรวจ type, lint, test กติกา ฐานข้อมูล และ browser รวมถึง build แอป | การเปลี่ยนโค้ดที่ทำให้ยอดผิดถูกตรวจพบอัตโนมัติ และมีรายงานผล |
| 8 | สร้าง image ระบุรุ่นด้วย commit เก็บใน Container Registry และ deploy รุ่นที่ผ่านการตรวจไป staging ด้วยข้อมูลสมมติ | เปิดใช้งานได้ health check ผ่าน และตรวจการแสดงยอดกับบันทึกวันบน staging ผ่าน |
| 9 | ซ้อม deploy รุ่นใหม่และ rollback ไป image รุ่นก่อน พร้อมตรวจข้อมูลที่บันทึก | รุ่นก่อนทำงานได้ และวันทบทวนที่บันทึกไว้ยังอยู่ |

เพิ่ม browser test ของตัวอย่างหลักเพื่อยืนยันว่าหน้าจอแสดงส่งจริง 60 กล่องและค้างส่ง 40 กล่อง ไม่จำเป็นต้องทำทุกกรณีซ้ำผ่าน browser ทั้งหมด

## แนวทาง deploy และ rollback

ใช้ image ที่ระบุรุ่นชัดเจนและผ่านการทดสอบแล้วในการ deploy และเก็บ image รุ่นก่อนสำหรับ rollback ผู้ให้บริการ Registry เครื่องปลายทาง และค่าใช้จ่ายจะตกลงก่อนขั้น deploy

การย้อนรุ่นแอปกับการกู้ฐานข้อมูลเป็นคนละงาน การเปลี่ยน image กลับไม่ย้อน schema หรือข้อมูลให้เอง จึงเริ่มจาก migration ที่ยังรองรับแอปรุ่นก่อน และซ้อม backup/restore ฐานข้อมูลแยกต่างหากก่อนพึ่งพากระบวนการกู้คืน

## ขอบเขตและจุดหยุด

- งาน R2 ครอบคลุมโค้ดและ tests แล้ว ใช้ requirement และ acceptance tests ฉบับปัจจุบันแทนยอดส่งจริงในแผนตั้งต้น
- หลังหน้าจอพร้อม ให้ผู้ใช้ตรวจตามขั้น 5 ก่อนเดินต่อเรื่อง deploy
- ไม่เชื่อม DBF หรือเข้าถึง `Y:\IG60` ในแผนรอบข้อมูลสมมติ
- การเชื่อมข้อมูลจริงเป็นงานรอบถัดไป หลังยืนยัน mapping และกติกาข้อมูล รวมถึงเทียบยอดคงเหลือและค้างส่งกับ Express ในรอบเวลาเดียวกันตาม requirement
