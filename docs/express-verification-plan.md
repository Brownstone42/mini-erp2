# รายการตรวจ Express ก่อนอ่านข้อมูลจริง

ร่างสำหรับผู้ใช้ตรวจ — 11 พฤศจิกายน 2026 อ้างอิง [Requirement R2](requirements.md) และ [Acceptance tests R2](acceptance-tests.md)

รอบนี้เตรียมรายการเท่านั้น ยังไม่อ่าน DBF ไม่เชื่อมแอป และไม่อัปโหลดข้อมูลจริงขึ้น cloud ข้อมูลธุรกิจจริงและภาพรายงานที่จะตรวจภายหลังต้องเก็บแยกจาก repository สาธารณะ เอกสารนี้ไม่มีข้อมูลลูกค้าจริง

## จุดประสงค์

ยืนยันว่าข้อมูลใน Express ตรงกับความหมายของยอดสั่ง ค้างส่ง และคงเหลือที่ Manager ต้องเห็น เริ่มจากถุงมือ Vinyl หนึ่ง SKU กิจการมีคลังเดียว ไม่มีการเพิ่มตัวเลือกคลังในแอป

ชื่อ SO, Invoice หรือชื่อไฟล์ DBF เพียงอย่างเดียวยังไม่ใช่หลักฐานว่าเป็นยอดสั่งหรือส่งจริง ต้องดูหน้าจอ เอกสาร และตัวอย่างการทำงานประกอบ การเคยพบรหัสลูกค้าในค้างส่งที่เชื่อมประวัติส่งขายได้ ไม่ได้ยืนยันแหล่งยอดสั่ง R2

## ขั้นแรก: ให้ผู้ใช้งาน Express ยืนยันหน้าจอและรายงาน

ยังไม่ต้องเตรียมทุกกรณีพร้อมกัน เริ่มจากสินค้าและคำสั่งซื้อหนึ่งใบ แล้วตรวจรายงานที่เกี่ยวข้องตามตาราง

| จุดตรวจ | สิ่งที่ต้องระบุ | ผลที่ต้องได้ |
| --- | --- | --- |
| สินค้า | รหัส Vinyl จริง ชื่อสินค้า หน่วยสั่ง/ส่ง/คงเหลือ อัตราแปลงหน่วยถ้ามี | ระบุ SKU และวิธีแสดงเป็นกล่องโดยไม่เดาหน่วย; VINYL-001 เป็นรหัสสมมติ |
| คลังเดียว | รหัสคลังที่ Express ใช้จริง ถ้ามีรหัสอื่นให้ยืนยันความหมาย | ขอบเขตคงเหลือถูกต้อง ไม่มีสินค้าในตำแหน่งอื่นปะปนโดยไม่ตั้งใจ |
| คำสั่งซื้อ | ชื่อเมนู/ชนิดเอกสาร ตัวอย่างใบสั่ง วันที่เอกสาร รหัสลูกค้า และรายการสินค้ารายบรรทัด | ยอดสั่งและวันที่ที่ใช้จัดเดือน ไม่ใช้วันที่ส่งหรือกำหนดส่งแทน |
| รายงานยอดสั่ง | ชื่อรายงาน ตัวกรอง วันที่เริ่ม/สิ้นสุด วิธีรวมบริษัท และสถานะเอกสารที่นับ | เทียบรายเดือนแยกบริษัทและยอดรวมได้ รวมถึงใบที่ส่งครบแล้ว |
| รายงานค้างส่ง | ชื่อรายงานและตัวกรองทั้งหมด เวลารายงาน ยอดสรุป SKU และรายละเอียด | รวมค้างทุกช่วงเวลา ทั้งงานเก่าและจองล่วงหน้าที่อยู่ในรายงาน; ไม่บวกสรุปซ้ำกับรายละเอียด |
| ยอดคงเหลือ | ชื่อหน้าจอ/รายงาน วันที่อ้างอิง และความหมายของยอด เช่น ยอดจริงหรือพร้อมขาย | ใช้ยอดตามความหมายที่ตกลง ไม่หักค้างส่งเอง |
| ส่งจริง | ชื่อเอกสาร วันที่ จำนวน และวิธีอ้างอิงบรรทัดคำสั่งซื้อ | ใช้หน้ารายละเอียดโดยไม่ทำให้ยอดสั่งซ้ำเมื่อส่งหลายครั้ง |
| MOQ / lead time | แหล่งข้อมูล ผู้ดูแลแก้ไข และหน่วย | ทราบว่าจะเก็บในแอปหรืออ่านจากแหล่งใด ไม่สมมติว่า Express มีให้ |

## กติกาที่ยังต้องตกลงก่อนเขียนตัวอ่าน

- ใบยกเลิก บรรทัดยกเลิก ปิดยอดค้าง และแก้จำนวนภายหลัง มีผลต่อยอดสั่งและรายงานค้างอย่างไร ยังไม่ตั้งชื่อว่า “ยอดสั่งสุทธิ” หรือกำหนดสูตรเอง
- การคืนสินค้า/ใบลดหนี้มีผลต่อยอดส่ง คงเหลือ หรือการเปิดค้างใหม่อย่างไร ตรวจแยกจากการยกเลิกคำสั่งซื้อ
- เอกสารร่าง/ยังไม่อนุมัติ/ลงวันที่ล่วงหน้าถูกนับในรายงานหรือไม่ งานจองที่สั่งแล้วและกำหนดส่งอนาคตต้องแยกจากเอกสารที่ยังไม่เกิด ณ เวลา snapshot
- รหัสลูกค้าใดใช้จับคู่บริษัท หากมีหลายสาขาหรือหลายรหัสของบริษัทเดียวกันจะรวมอย่างไร ไม่รวมด้วยชื่อที่คล้ายกันเอง
- เอกสารหนึ่งใบมีสินค้าเดิมหลายบรรทัดหรือส่งอ้างอิงหลายใบได้หรือไม่ ต้องระบุคีย์เอกสารและบรรทัดที่ไม่ซ้ำ
- วันที่เป็นรูปแบบใดและใช้ปี พ.ศ./ค.ศ. อย่างไร เวลาที่อ่านข้อมูลและเวลาที่รายงานอ้างอิงต้องจดแยกให้ชัด

## ตัวอย่างที่จะใช้เทียบภายหลัง

จำนวนด้านล่างเป็นตัวอย่างสมมติ ไม่ใช่ยอดที่คาดว่าต้องพบจริง ให้เลือกเอกสารจริงที่มีพฤติกรรมเทียบเคียงโดยไม่แก้ข้อมูล Express เพื่อสร้างกรณีทดสอบ

| กรณี | สิ่งที่ต้องตรวจ |
| --- | --- |
| สั่ง 100 ส่ง 60 | ตารางสั่งนับ 100 ในเดือนสั่ง; ค้างใช้ค่าจากรายงาน Express (ตัวอย่าง 40) ไม่สร้างจากสูตรแทน |
| ส่งหลายครั้งคนละเดือน | ยอดสั่งนับครั้งเดียว ส่วนรายการส่งอยู่รายละเอียดตามวันส่ง |
| ส่งครบ | ยอดสั่งยังนับในเดือนสั่ง และค้างเป็น 0 เมื่อข้อมูลรายงานครบและยืนยันแล้ว |
| งานค้างเก่ากว่า 12 เดือน | ไม่เข้าในตารางสั่ง 12 เดือน แต่ยังอยู่ยอดค้างถ้ารายงาน Express มี |
| สั่งเดือนนี้ กำหนดส่งอนาคต | ยอดสั่งอยู่เดือนสั่ง ค้างรวมงานจองที่อยู่ในรายงาน |
| เดือนที่ไม่สั่ง | แสดง 0 ได้เมื่อยืนยันว่าข้อมูลครบ ไม่ใช้ 0 แทนรายงานที่อ่านไม่ได้ |
| ยกเลิก/คืน/ปิดรายการ/หลายหน่วย | จดผลจริงและตกลงกติกาก่อนเพิ่ม fixture และ acceptance test |

ถ้าไม่พบกรณีใด ให้บันทึกว่า “ยังไม่พบตัวอย่าง” ไม่อ้างว่าตรวจผ่าน

## ขั้นที่สอง: เสนอแผนสำรวจ DBF เพื่ออนุมัติแยก

หลังตรวจรายการนี้แล้ว จึงเสนอวิธีอ่านแบบ read-only ที่ `Y:\IG60` โดยไม่แก้ DBF หรือไฟล์ประกอบของ Express และไม่รบกวนผู้ใช้งาน สำรวจเฉพาะไฟล์/ฟิลด์ที่จำเป็น ไม่กวาดข้อมูลลูกค้าทั้งหมดขึ้น Git หรือ cloud

ผลที่ต้องได้คือ mapping: ความหมายข้อมูล → ไฟล์/ฟิลด์จริง → คีย์เอกสาร/บรรทัด → รหัสลูกค้า/SKU → สถานะ/หน่วย/วันที่ พร้อมหลักฐานที่ยังขาด การคัดลอกหลายไฟล์ขณะ Express มีการเขียนอาจไม่เป็น snapshot เดียวกัน จึงต้องตกลงช่วงเวลาและวิธีเก็บข้อมูลที่สอดคล้องกันก่อนเทียบยอด

## ขั้นที่สาม: ตรวจยอดในรอบเวลาเดียวกัน

กำหนดเวลาตัดข้อมูลและขอบเขตร่วมกับผู้ใช้งาน Express จดตัวกรองรายงานทุกครั้ง ตารางสั่งใช้เดือนปัจจุบันรวมย้อนหลัง 11 เดือนถึงเวลาอ้างอิง ส่วนค้างส่งไม่ถูกจำกัดด้วยช่วงตาราง

| ตัวชี้วัด | รายงาน Express | ผลอ่านแบบ read-only | ส่วนต่าง | ผลตรวจ/เหตุผล |
| --- | --- | --- | --- | --- |
| ยอดสั่งแต่ละบริษัท/เดือนและรวม | รอตรวจ | รอตรวจ | รอตรวจ | ยังไม่ยืนยัน |
| ค้างส่งรวม SKU ทุกช่วงเวลา | รอตรวจ | รอตรวจ | รอตรวจ | ยังไม่ยืนยัน |
| ผลรวมรายละเอียดค้างเทียบยอดสรุป | รอตรวจ | รอตรวจ | รอตรวจ | ยังไม่ยืนยัน |
| คงเหลือ | รอตรวจ | รอตรวจ | รอตรวจ | ยังไม่ยืนยัน |

ผ่านเมื่อยอดตรงภายใต้เวลา ตัวกรอง และหน่วยเดียวกัน หรือมีคำอธิบายส่วนต่างที่ตรวจสอบแล้วและได้รับการยอมรับ ไม่ใช้การปรับตัวเลขให้ตรงเพื่อกลบความต่าง หากข้อมูลขาดให้คงสถานะ “ข้อมูลไม่พร้อม” หากยังไม่เทียบให้คง “ยังไม่ยืนยันกับ Express”

จากนั้นจึงเสนอแผนนำข้อมูลเข้าแอป การป้องกันข้อมูลจริง และ acceptance tests เพิ่มให้ผู้ใช้ตรวจก่อนดำเนินการ
