# Mini-ERP V2

## Staging access

เพิ่มรหัสผ่านสำหรับ staging แล้ว ดู [การตั้งค่า Render และแผนซ้อม rollback](docs/staging-access.md) ต้องตั้งค่าลับและ deploy รุ่นที่มีการป้องกันก่อนจึงจะมีผลจริง ใช้เฉพาะข้อมูลสมมติ ยังไม่เชื่อม DBF

## CI

เชื่อม [GitHub repository แบบ public](https://github.com/Brownstone42/mini-erp2) แล้ว ทุก push และ pull request จะตรวจ TypeScript, Vitest, production build และ Playwright กับ PostgreSQL ชั่วคราว ดู [ผล CI ล่าสุด](https://github.com/Brownstone42/mini-erp2/actions/workflows/ci.yml) และ [คู่มือ CI](docs/ci.md) ทดลองกระบวนการบน Linux ได้ด้วย `docker compose -f compose.ci.yaml up --build --abort-on-container-exit --exit-code-from checks` ยังไม่ deploy หรือเชื่อม DBF

## เปิดชุด Docker แยกจากฐานเดิม

ใช้ `npm run docker:up` แล้วเปิด http://127.0.0.1:3300 ชุดนี้ใช้ `compose.docker.yaml` และ volume ของตัวเอง ไม่ใช้ฐานทางสำรองเดิมหรือ DBF

ปิดด้วย `npm run docker:down` (เก็บข้อมูลไว้) ดูสถานะด้วย `npm run docker:status` และตรวจการบันทึกวันข้ามการสร้าง containers ใหม่ด้วย `npm run test:docker` ซึ่งจะตั้งวันในฐาน Docker demo เป็น 25 พ.ย. 2026 ดู [คู่มือ Docker](docs/docker-local.md)

## สถานะล่าสุด: R2

หน้าหลักใช้ยอดสั่งรายเดือน 12 เดือนแยกบริษัทและยอดรวม พร้อมคงเหลือ 150 / สั่ง 180 / ค้างส่งตามรายงานสมมติ 70 กล่อง ไม่มีตัวเลือกคลัง (กิจการมีคลังเดียว) ยอดค้างไม่ใช้สูตรสั่งลบส่งและไม่ถูกจำกัดด้วยช่วงตาราง

กดชื่อบริษัทเพื่อเปิดคำสั่งซื้อเทียบส่งจริง หรือกด “ดูรายละเอียดค้างส่ง” เพื่อดูบริษัท เอกสาร วันที่สั่ง กำหนดส่ง และยอดค้าง ใช้ลิงก์ตัวอย่างบนหน้าหลักลองงานเก่า งานจอง หรือทั้งสองกรณีได้ กรณีรวมงานเก่าและงานจอง: ยอดสั่ง 230 / ค้าง 130 / คงเหลือ 150 กล่อง ทุกยอดยังระบุว่าไม่ยืนยันกับ Express

รัน `npm run test:r2` เพื่อตรวจ logic R2 และ browser ทั้งชุด หรือ `npm test` เพื่อตรวจ logic ทั้งเดิมและ R2 ดู [ผลตรวจและ coverage ทั้ง 20 AT](docs/r2-validation.md)

ผลล่าสุด: logic 45 tests ผ่าน, browser 23 tests ผ่าน, TypeScript และ production build ผ่าน ตรวจภาพ desktop/มือถือแล้ว

วันทบทวนใช้ PostgreSQL และคีย์คลังภายในที่มีอยู่ ไม่มี UI ให้เลือกคลังและไม่มีการเพิ่มความสามารถหลายคลัง ฐานพัฒนา local เดิมยังเก็บไว้ ส่วนชุด Docker ใหม่ใช้ฐานและ volume แยก ผ่านการตรวจบันทึกวันข้ามการสร้าง containers ใหม่แล้ว ไม่ได้ล้างฐานพัฒนาหรือเชื่อม DBF

ส่วนด้านล่างเป็นบันทึกการพัฒนา R1 ตามลำดับเวลา ตัวเลขยอดส่งและผล tests ในแต่ละช่วงเป็นประวัติ ไม่ใช่ requirement หน้าหลักล่าสุด

## AT-04 ช่วงรายงาน 12 เดือน

`tests/acceptance/at-04.test.ts` ตรวจช่วงเดือนสำหรับตารางรายงาน โดยส่งเวลาอ้างอิงข้อมูลเข้าไปตรง ๆ ไม่อาศัยเวลาปัจจุบันของเครื่อง:

1. เวลาไทย 10 พฤศจิกายน 2026 เวลา 09:00 น. ต้องได้เดือนธันวาคม 2025 ถึงพฤศจิกายน 2026 ครบ 12 เดือน เรียงเก่าไปใหม่ และระบุพฤศจิกายนเป็นเดือนที่ยังไม่ครบ
2. เวลา UTC 31 ธันวาคม 2026 เวลา 18:00 น. คือเวลาไทย 1 มกราคม 2027 เวลา 01:00 น. ต้องได้ช่วงกุมภาพันธ์ 2026 ถึงมกราคม 2027 โดยเดือนสุดท้ายคือมกราคม ไม่ใช่ธันวาคม

`src/replenishment/reporting-period.ts` แปลงเวลาอ้างอิงเป็นปีและเดือนตาม Asia/Bangkok แล้วไล่เดือนย้อนหลัง 11 เดือน รวมเดือนอ้างอิงเป็น 12 เดือน ใช้เดือนปฏิทิน ไม่หักย้อนหลัง 365 วัน

ผลลัพธ์มี `months` พร้อม `isPartial` ของเดือนปัจจุบัน และ `asOf` พร้อม `timeZone` สำหรับหน้าจอแสดงข้อมูลถึงเวลาใด โดย `2026-11-10T02:00:00.000Z` คือเวลาไทย 09:00 น. ไม่ใช่เวลาอ้างอิงใหม่ ส่วน `isPartial: false` ของเดือนก่อนหน้าหมายถึงเดือนปฏิทินสิ้นสุดแล้ว ไม่ใช่การยืนยันว่าข้อมูลต้นทางครบถ้วน

AT-04 ตรวจส่วนกำหนดช่วงเดือนและ metadata การเชื่อมช่วงเดือนกับการกรองรายการส่งเพิ่มใน AT-05 ส่วนการเติมยอด 0 อยู่ใน AT-06 และยังไม่ได้ทำหน้าจอ

## AT-05 กรองรายการส่งตามช่วงรายงาน

`tests/acceptance/at-05.test.ts` เรียก `reviewCustomers(orders, period)` โดยใช้ช่วงที่สร้างจาก AT-04 ตรวจทั้งยอดรายบริษัท รายเดือน และยอดรวม

ตัวอย่างคำสั่งซื้อ 100 กล่อง อ้างอิงข้อมูลวันที่ 10 พฤศจิกายน 2026 เวลา 09:00 ประเทศไทย:

| วันที่ส่ง | จำนวนกล่อง | การนับในรายงาน |
| --- | ---: | --- |
| 30 พ.ย. 2025 | 10 | ก่อนช่วง ไม่รวมยอดส่งในรายงาน แต่หักยอดค้าง |
| 1 ธ.ค. 2025 | 20 | วันเริ่มช่วง รวมยอดส่ง |
| 10 พ.ย. 2026 | 30 | วันอ้างอิง รวมยอดส่ง |
| 11 พ.ย. 2026 | 5 | อนาคต ไม่รวมและยังไม่หักยอดค้าง |

ผลคือส่งจริงในช่วง 50 กล่อง และค้างส่ง 40 กล่อง โดยยอดค้างคำนวณจาก 100 − (10 + 20 + 30) ไม่ใช่ 100 − 50 จึงไม่ทำให้ของที่เคยส่งก่อนช่วงรายงานกลับมาเป็นยอดค้าง

กรณีที่สองตรวจวันสิ้นสุดตามเวลาไทย: UTC วันที่ 31 ธันวาคม เวลา 18:00 เป็นวันที่ 1 มกราคมในไทย จึงรวมรายการส่ง 1 มกราคม และตัดรายการ 2 มกราคมออก

ข้อมูลสมมติมีวันที่ส่งระดับวัน (YYYY-MM-DD) เท่านั้น จึงกรองได้ถึงวันอ้างอิง รายการในวันเดียวกันต้องมาจาก snapshot ณ เวลาอ้างอิงอยู่แล้ว ยังไม่สามารถแยกรายการก่อนหรือหลัง 09:00 ของวันเดียวกันได้ การยืนยัน snapshot จริงยังอยู่ในงานเชื่อม Express ภายหลัง

หากไม่ส่ง `period` ฟังก์ชันยังรวมทุกรายการตามพฤติกรรมเดิมของ AT-01 ถึง AT-03

### เริ่ม PostgreSQL สำหรับพัฒนา

ติดตั้ง dependencies ด้วย `npm ci` (มี Prisma generate ใน postinstall) และติดตั้งเบราว์เซอร์ด้วย `npx playwright install chromium` คัดลอก `.env.example` เป็น `.env` ถ้ายังไม่มีไฟล์เดิม

ทางเลือกปกติเมื่อ Docker พร้อม:

```sh
npm run db:up
npm run db:migrate
npm run dev
```

เครื่องที่ตรวจรอบนี้ Docker daemon เริ่มไม่ได้ และ `wsl --status` รายงานว่ายังไม่ได้ติดตั้ง WSL จึงใช้ PostgreSQL 17 แบบ project-local จาก `embedded-postgres` เป็นทางสำรอง ยังคงใช้ PostgreSQL/Prisma จริง ไม่มีการติดตั้ง WSL รีสตาร์ตเครื่อง หรือเปลี่ยนเป็น SQLite

เปิด Terminal แรกแล้วรันค้างไว้:

```sh
npm run db:local
```

จากนั้นใน Terminal อีกหน้าต่าง:

```sh
npm run db:migrate
npm run dev
```

`db:local` เก็บข้อมูลไว้ใน `.local-postgres` ซึ่งไม่เข้า Git หยุดด้วย Ctrl+C แล้วเริ่มใหม่ได้โดยข้อมูลยังอยู่ ใช้พอร์ตเดียวกับ Compose จึงเลือกใช้ทีละวิธี ข้อมูลของ runtime local และ Docker volumes อยู่คนละที่และไม่ได้ย้ายข้ามกันอัตโนมัติ Runtime สำรองใช้สำหรับพัฒนาเท่านั้น ส่วน Compose เตรียมไว้แต่ยังไม่ได้รันยืนยันบนเครื่องนี้

## AT-14 ข้อมูลไม่พร้อมและยังไม่ยืนยันกับ Express

เพิ่ม `presentMetric` ใน `src/replenishment/data-status.ts` แยกค่าตัวเลขออกจากสถานะข้อมูล:

| ข้อมูลเข้า | หน้าจอ |
| --- | --- |
| ไม่มีข้อมูล (`null`) | — และ “ข้อมูลไม่พร้อม” พร้อมเหตุผล |
| มีข้อมูลเป็น 0 | 0 กล่อง พร้อมสถานะการยืนยัน |
| มีข้อมูลแต่ยังไม่เทียบ Express | ตัวเลขเดิม และ “ยังไม่ยืนยันกับ Express” พร้อมเวลาข้อมูล |
| มีข้อมูลและยืนยันแล้ว | “ยืนยันกับ Express แล้ว” (ทดสอบ logic ด้วยข้อมูลสมมติเท่านั้น) |

ค่า null มีลำดับความสำคัญเหนือ flag ยืนยันที่อาจค้างมา จึงไม่แสดงยืนยันเมื่อข้อมูลขาด ปัจจุบัน `demo-metrics.ts` คำนวณการ์ดและตารางจากชุดคำสั่งซื้อสมมติ แล้วจำลองสถานะขาดแยกแต่ละส่วน จำนวนปกติคือ 150/110/70 ตามตัวอย่างในเอกสาร ยังไม่เชื่อม DBF และไม่สามารถกดยืนยันข้อมูลจริงได้ การส่งข้อมูลไม่ครบเข้า aggregation เป็น array ว่างอาจได้ 0 ที่ผิดความหมาย จึงต้องแยกสถานะความพร้อมตั้งแต่จุดรับข้อมูล

บนหน้าหลักมีลิงก์ลองข้อมูลขาดทั้งสามส่วนและคงเหลือเป็นศูนย์ ส่วนที่มีข้อมูลยังแสดงค่าของตนเอง ข้อมูล demo ทุกตัวเลขมีป้ายยังไม่ยืนยัน เวลาสมมติตรึงที่ 10 พ.ย. 2026 เวลา 09:00 น. Asia/Bangkok

Red ก่อนเขียน logic: `npm test` ได้ 5 failed (AT-14) และ 22 passed (เดิม) เพราะฟังก์ชันสถานะยังไม่ implement หลังเพิ่ม logic รัน `npm run test:at-14` ผ่าน Vitest 5 tests และ Playwright 5 tests ครอบคลุมยอดไม่ยืนยัน ข้อมูลขาดแต่ละส่วน และศูนย์จริง ภาพอยู่ใน `test-results/at-14-unverified.png` และ `test-results/at-14-unavailable.png`

ผลตรวจรวมหลัง AT-14: `npm test` ผ่าน 27 tests, `npm run test:e2e` ผ่าน 9 tests, `npm run typecheck` ผ่าน และ production build ผ่านโดยตั้ง `BUILD_CHECK=1` ให้ใช้ `.next-build` แยกจาก dev server

## เชื่อมตารางยอดรายเดือนเข้าหน้าเว็บ

ใช้ `src/replenishment/demo-orders.ts` เป็นรายการสั่ง/ส่งสมมติ (ไม่มีการใส่ยอดค้างเป็นคำตอบไว้ใน input) แล้วเรียก `buildReportingPeriod` และ `reviewReplenishment` ที่ผ่านการทดสอบแล้ว `buildDemoReview` คืนผลให้ทั้งการ์ดและ `src/app/customer-table.tsx` จึงไม่ใส่ยอด 110/70 ตายตัวไว้บนหน้าเว็บ

- บริษัทเอ: สั่ง 100 ส่ง ต.ค. 60 รวมส่ง 60 ค้าง 40
- บริษัทบี: สั่ง 80 ส่ง ก.ย. 30 และ ต.ค. 20 รวมส่ง 50 ค้าง 30
- รวม: ก.ย. 30 ต.ค. 80 ส่งจริง 110 ค้าง 70; คงเหลือยังเป็น 150 แยกต่างหาก
- ตารางครบ 12 เดือน ธ.ค. 2025–พ.ย. 2026 พร้อมระบุเดือนปัจจุบันยังไม่เต็มเดือน เดือนที่ข้อมูลครบแต่ไม่มียอดแสดง 0
- แสดงสถานะส่งจริงและค้างส่งแยกกัน เมื่อจำลองข้อมูลส่วนใดขาด ช่องรายละเอียดและยอดรวมส่วนนั้นเป็น — พร้อมคำอธิบาย ไม่กระทบอีกส่วน
- ตารางเลื่อนแนวนอนได้ ใช้หัวแถว/หัวคอลัมน์และหน่วยกล่องชัดเจน รองรับการโฟกัสด้วยคีย์บอร์ดและหน้าจอมือถือ

รันเฉพาะงานนี้ด้วย `npm run test:customer-table` (ใช้ฐานข้อมูลทดสอบและพอร์ต 3100 ตาม Playwright config เดิม)

Red: browser tests ใหม่ทั้ง 4 ข้อล้มเหลวเพราะไม่พบตารางและสถานะที่ต้องแสดง ก่อนแก้โค้ดแอป จากนั้น Green: tests เดิมทั้ง 4 ข้อผ่าน โดยตรวจทุกเดือนของสองบริษัทและแถวรวม ตรวจข้อมูลขาดสองส่วน และตรวจการเลื่อนตารางบนมือถือ ภาพอยู่ที่ `test-results/customer-table-desktop.png` และ `test-results/customer-table-mobile.png`

การตรวจตารางบนเว็บครั้งนี้ใช้ชุดตัวอย่างหลัก ส่วนกรณีขอบเขตวันที่ คำสั่งซื้อเก่า และ SKU/คลังอื่น ยังมีหลักฐานทดสอบระดับ logic จาก AT เดิม ไม่ได้เพิ่ม browser scenario ครบทุกกรณี ยังไม่มีข้อมูลจริงหรือการยืนยันยอดกับ Express

ผลตรวจหลังเชื่อมตาราง: Vitest 27 tests ผ่าน, Playwright ทั้งชุด 13 tests ผ่าน, TypeScript ผ่าน และ production build ผ่านใน `.next-build` ตรวจภาพ desktop และมือถือแล้ว
